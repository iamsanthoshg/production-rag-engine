# Pipecat Real-Time Voice Processing Architecture

Pipecat is an open-source framework designed for building ultra-low-latency real-time voice and multimodal conversational agents.

## Core Concepts

### 1. The Frame Pipeline
Pipecat is structured as a directional pipeline of **Frame Processors**. Data travels through the pipeline as discrete objects called **Frames**.
- **AudioRawFrame**: Raw PCM audio samples (typically 16kHz or 24kHz mono).
- **TextFrame**: Transcribed words or tokens generated by an STT engine or LLM output.
- **LLMFullResponseStartFrame / EndFrame**: Signal boundaries for LLM turn completion.
- **InterruptionFrame**: Broadcasted when user speech is detected while the bot is speaking, canceling in-flight generation and clearing audio buffers.

### 2. Pipeline Execution Flow
A standard voice assistant pipeline follows this sequence:

```
[Microphone / WebRTC Transport]
             ↓
     [AudioRawFrame]
             ↓
  [Voice Activity Detector (VAD)] (e.g. Silero VAD)
             ↓
 [Speech-to-Text (STT) Service] (e.g. Deepgram, Whisper)
             ↓
       [TextFrame]
             ↓
    [Context Aggregator] (Appends to conversation history)
             ↓
        [LLM Service] (e.g. Groq, OpenAI, Anthropic)
             ↓
       [Token Frames]
             ↓
 [Text-to-Speech (TTS) Service] (e.g. Cartesia, ElevenLabs)
             ↓
     [AudioRawFrame]
             ↓
  [Speaker / WebRTC Transport Output]
```

### 3. Handling Barge-In & Interruptions
Ultra-low latency requires responsive interruption handling:
- When the VAD fires during agent playback, a `UserStartedSpeakingFrame` triggers an `InterruptionFrame`.
- Downstream processors (LLM queues, TTS synthesizers, and audio output sinks) immediately discard unplayed audio chunks and cancel active streaming HTTP/WebSocket tasks.
- This maintains conversation fluidness under sub-500ms voice turn-around times.
